# 角色、作用范围与有效权限

本文说明 login 如何把权限组合成角色、角色在什么范围内有效、用户组如何间接赋权，以及
“某人实际能做什么”如何计算。模型的关键点：**角色属于某个作用范围，权限有数据范围，
应用之间互不相通**。

## 1. 术语

- **作用范围（scope）**：权限/角色有效的位置。分 **系统级**（整个 login 实例）与
  **应用级**（某个应用内部）。一个角色只属于一个作用范围。
- **系统角色**：系统级角色的权限组合；预设角色随初始化创建，也可由管理员创建普通角色。
- **应用角色**：每个应用创建时按模板生成**该应用专属**的角色（`app_admin`、
  `app_user`），不同应用的同名角色是不同记录，不能跨应用关联。
- **用户组**：一批用户的集合；可直接给组分配角色，组内成员间接受益。
- **数据范围**：同一条权限能操作哪些数据。`all`＝不限；`resources`＝仅列出的资源；
  `none`＝不允许任何数据；`undefined`＝未声明（资源检查默认拒绝）。
- **委派**：把角色/权限转授他人。系统区分“可使用（可直接行使）”和“可转授（可以再交给
  别人）”；自我提权、缺少转授资格、目标超出范围都会被拒绝。
- **有效权限**：某用户在某应用/系统范围内当前实际拥有的权限集合 = 直接角色 + 用户组
  角色 + 委派等来源合并后，再与应用成员状态、权限启停、数据范围取交集。
- **权限目录**：权限定义的登记表，按作用范围区分：系统内置权限（随版本提供，受保护）、
  系统自定义权限（管理员登记）、应用独有权限。每项权限有稳定的**机器标识**（程序判定
  用）与中文名称/说明/限制（展示用）；机器标识创建后不可改。
- **root_only（敏感权限）**：只能由 root 或受控本地通道行使的权限，不能组合进普通角色，
  Web 管理页面也不能启停；它不是“给管理员用的普通权限”。

## 2. 五个预设系统角色（初始化时创建）

| 角色 | 默认权限（要点） | 明确不能做什么 |
|---|---|---|
| 系统管理员 `system_admin` | 用户、组、角色、权限目录、应用、会话强制退出、审计查看/导出、报告、备份（创建/查看/取消/保留/清理）、常规设置、诊断 | 不能修改敏感操作规则、恢复备份、清理审计、操作 root 或自行扩大授权；范围仅限 root 交给他的范围 |
| 用户管理员 `user_admin` | 用户查询/创建/修改/禁用、发起密码找回、强制会话退出 | 不能操作 root/高权限账户，不能修改权限分配 |
| 客服 `support` | 发起密码找回、求助单查询/登记/更新；被 root 逐项授予后可管理端直接改名/直接重置密码（需操作者本次两步验证） | 默认不能查看/指定密码、改邮箱再重置、清除两步验证、冒充用户、操作高权限账户；直接重置也不能读取旧口令/MFA 种子/恢复码或重置 root |
| 审计员 `auditor` | 审计查看/导出、报告查看/生成/导出/定期报告 | 不能改用户、改权限或删除原始记录 |
| 普通用户 `normal_user` | 本人资料、凭证、会话、应用授权 | 仅限自己；敏感修改仍需再次验证 |

同时预置五个**空**用户组（系统管理员组、用户管理员组、客服组、审计员组、普通用户组）。
初始化只建组，**不自动加人**；成员关系必须显式建立。

说明：预设角色是默认模板；root 可创建普通角色并组合目录中允许转授的权限。`root_only`
的权限与操作不会出现在可组合列表中，服务端还会再次拒绝。

## 3. 应用内角色与成员

每个应用创建时生成：

| 应用角色/用户组 | 默认 | 说明 |
|---|---|---|
| `app_admin`（应用管理员角色） | 应用内权限为空 | 管理指定应用资料、成员、应用内角色与应用独有权限；不能跨应用、不能改共享密码 |
| `app_user`（应用普通用户角色） | 应用内权限为空 | 登录已加入的应用，使用明确分配的业务功能；加入应用不等于自动拥有全部功能 |
| `app-administrators` / `app-users` 用户组 | 空组 | 对应角色的默认成员组，初始化不自动加入成员 |

应用独有权限由应用管理员按需登记；它们只在该应用内有效。**同名权限跨应用不通用**：
在 A 应用取得 `report.approve`，不代表在 B 应用拥有同名权限。

## 4. 有效权限如何计算（业务服务应遵守）

1. 从可信身份确定“用户 + 应用 + 当前时间”；
2. 检查账户状态与应用成员关系（成员停用即不再有该应用权限）；
3. 汇总来源：直接角色、用户组角色、委派；检查角色与权限是否启用；
4. 对每条权限按数据范围取交集（多来源时 `undefined` 优先拒绝，`none` 优先拒绝，
   `resources` 取交集）；
5. 联合令牌 scope（如有）后得到最终可执行集合；**不缓存**，每次按当前状态判定；
6. 判定失败或依赖不可用 → 默认拒绝（`AUTHZ_UNAVAILABLE`），不降级放行。

业务服务还必须自行校验**资源归属与对象状态**（例如“这张报销单是不是这个用户的”），
功能权限不能替代归属检查。

## 5. 作用范围与数据范围的区别

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| 作用范围 | 这条权限/角色在哪个域有效？ | 系统级 `users.read`；应用级“审批本应用单据” |
| 数据范围 | 同一条权限能碰哪些数据？ | `all` 全部；`resources` 指定应用/资源集合；`none` 无 |
| 应用成员 | 这个用户属于这个应用吗？ | 未加入应用 → `APP_MEMBERSHIP_REQUIRED` |
| Token audience | 令牌面向哪个资源？ | audience 与业务资源不一致 → `TOKEN_AUDIENCE_MISMATCH` |

这四层是**独立校验**，不能互相替代。常见错误：

- 用请求参数里的 `app_id` 冒充调用应用 → `APP_SCOPE_MISMATCH`；
- 令牌有效就直接放行 → 忽略成员/权限/数据范围；
- 用应用内的一个功能权限代替资源归属检查；
- 把“角色默认权限”当成“当前实际权限”（页面必须同时展示默认值与真实值）。

## 6. 委派与自我提权

- 分配角色/权限前，服务端复核操作者可委派范围；目标、动作、范围任一变化都要重新检查。
- **自我提权**（给自己加权限）、缺少转授资格、跨范围分配都被拒绝并写审计。
- 委派资格分“可使用”和“可转授”，签发/撤回只允许受信本地/系统通道。
- 角色组合、组成员变更、权限启停、预设恢复都会改变实际权限，必须重新检查并记录审计
  ——不能只保护“分配角色”这一个入口。

## 7. 权限目录的创建、删除与启停（系统管理页面）

系统管理页面 `/admin/permissions*` 直接连接真实 permission 服务，不是只展示按钮：

- **创建自定义权限**：`/admin/permissions/create` 选择作用范围、填写机器标识与中文
  名称/说明/限制。页面与适配器固定 `is_builtin=false`、`root_only=false` —— 不能通过
  表单创建内置权限或 root_only 权限。同一范围内机器标识重复返回冲突（409）。
- **删除自定义权限**：只有非内置权限可删除；仍被 `role_permissions` 引用时服务端在
  同一事务条件删除中拒绝（409），不会隐式级联破坏角色授权。删除保留审计历史。
- **内置权限启停**：内置权限不可修改、不可删除，只能启用/停用；`root_only` 内置权限
  只能由受限本地初始化操作者启停。停用是“拒绝”而不是“跳过检查”：权限引擎按当前
  状态实时计算，停用后持有该权限的角色立即不再生效（组合关系保留，重新启用后恢复）。
- **影响预览**：权限详情按真实角色组合列出引用该权限的角色与启停状态，并给出删除
  阻塞原因；缺少 `roles.read` 时只降级隐藏该列表，不改变授权判定。
- **行版本冲突**：`permissions` 表没有独立 `row_version` 列，页面用记录 `updated_at`
  毫秒值作为乐观锁；基于旧页面提交返回 409 并重新读取当前状态，避免覆盖他人修改。
  写入前仍由服务端重新鉴权，TOCTOU 由领域服务与再次认证兜底。
- **管理强认证与敏感确认**：创建、删除与内置权限启停属于敏感目录变更，表单必须显式
  确认，并经过真实 reauth/policy 链（操作目录 `permission.catalog.change`）复核近期
  强认证；宿主未装配再次认证回调时这些动作 fail-closed 拒绝。页面确认框不是授权。
- **服务端重鉴权与审计**：每次读/写都由适配器重新构造可信 Caller、复核管理授权与作用
  范围；创建/修改/启停/删除与读取写真实审计，重复提交按幂等或冲突结果记录，不产生
  虚假成功。

## 8. 预设初始化与恢复

- 预设角色/用户组/权限目录是**版本化**的，初始化幂等；重复执行不会重复创建。
- 页面可查看“目录默认值 vs 当前组合”的差异；恢复默认只在受信通道执行，并需要明确的
  作用域与版本，不能“一键覆盖”后不记录。
- 初始化不会自动给任何人加角色，也不会创建 root；root 由受控首次初始化流程单独创建。

## 10. 公开 Go RBAC 接口（步骤 224）

`Runtime.RBAC()` 返回按领域分组的服务，宿主无需导入 `internal/`：

```go
rbac := runtime.RBAC()
rbac.Roles()        // Get/Update/Enable/Disable/Delete/AddPermission/RemovePermission/
                    // List/ListPermissions/ListAssignments/AssignUser/RevokeUser/AssignGroup/RevokeGroup
rbac.Groups()       // Create/Get/Update/Delete/List/ListMembers/AddMembers/RemoveMembers
rbac.Permissions()  // Create/Get/Update/Enable/Disable/Delete/List/Catalog
rbac.Authorization()// Check/EffectivePermissions/PermissionSources/CheckResourceAccess
rbac.Delegations()  // Grant/Revoke/Get/List/DelegatablePermissions
rbac.Presets()      // Catalog/Preview/Restore
```

边界与约定：

- 身份只来自 `AdminCaller`：`LocalAdmin()` 是宿主进程受信操作者；`AdminSession(secret)`
  是真实完整用户会话，受限会话在解析阶段拒绝。领域服务在事务内复核系统/应用范围权限与
  可委派范围，公开门面不因“不经过 HTTP”而绕过敏感策略、root 保护或审计失败回滚。
- 列表复用 `AdminPage`/既有 `AdminList*` 请求结果（步骤 216/217），有界遍历直接用
  `IterateAdminPages`（步骤 220）；自定义权限只在指定 scope 生效，同名系统/应用权限隔离。
- 预设 `Preview`/`Restore` **只接受 `LocalAdmin`**；`AdminSession`（普通管理员/受限会话）
  返回 `ACCESS_DENIED`，不能通过公开 Go 入口恢复高权限预设。恢复只接受预览签发的短时
  单次令牌；`Catalog` 含真实 `Implemented` 标记与中文“能做什么/生效范围/不能做什么”。
- 委派资格只表示“可转授上限”，不授予系统资格；签发/撤回只接受受信通道，普通用户只能
  读取自己的资格与可转授权限；所有实际赋权仍经同一 Guard 复核。
- 可运行外部示例：`examples/rbac-consumer`（独立 module，仅导入公开包，临时 SQLite 自清理）。
