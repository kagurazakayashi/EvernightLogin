# 应用与权限

本文说明“应用（Application）”是什么、成员关系如何隔离权限，以及系统权限与应用独有
权限的区别。权限键与中文说明以代码目录（`internal/preset/catalog.go`）为准；本文列出
当前全部 51 个系统权限键。

## 1. 核心概念

- **应用（Application）**：接入 login 的业务系统。应用 ID（同时是 OAuth `client_id`）
  创建后不变；应用有独立资料、成员、角色、应用独有权限与凭证。
- **应用成员**：用户必须先是应用成员，才可能在该应用内获得权限。成员关系与应用内资料
  和应用隔离，不能用一个同名角色或请求参数里的 `app_id` 冒充。
- **系统权限**：作用范围是系统级（例如“查看普通用户”“管理备份”）。
- **应用独有权限**：只属于某个应用、只在该应用内有效；即使标识同名，也与其他应用的
  同名权限互不相通（跨应用使用会得到 `APP_SCOPE_MISMATCH`/`PERMISSION_REQUIRED`）。
- **权限联合校验**：Token 有效 ≠ 有权操作。实际放行取“令牌 scope ∩ 当前有效权限 ∩
  应用/成员状态 ∩ 数据范围”的交集（见 [login-and-oauth.md](login-and-oauth.md) 第 6 节）。

## 2. 应用生命周期与安全边界

| 操作 | 规则 |
|---|---|
| 创建应用 | 需要相应管理权限；应用 ID/作用范围创建后不可变 |
| 修改资料 | 按权限修改显示资料；负责人字段只在宿主显式允许时可改，变更**不会**自动转移权限 |
| 成员管理 | 只影响当前应用；成员停用/移除即时影响该应用的权限判定 |
| 启停应用 | 停用后该应用的令牌/权限判定按拒绝处理；停用可恢复，不是删除 |
| 删除应用 | 独立生命周期操作（步骤 190）：必须已停用，执行**逻辑删除**后客户端凭证/旧令牌/会话/权限判定立即按拒绝处理；成员/角色/权限/客户端/授权记录与审计保留供追溯，不可再启用/改资料；物理清理只允许受控本地/系统通道在保留期（默认 30 天）后执行，保留共享账户与安全审计 |
| 客户端凭证 | 秘密只在登记/轮换成功响应中出现一次；元数据页只显示编号/前缀/状态/到期 |
| 公开客户端 | 不能安全保存内置密钥，不提供创建 secret 的入口；必须走 PKCE |
| 回调地址 | 必须精确匹配登记值；危险回调（如非 https 外部地址）会被真实拒绝 |
| 应用 Webhook | 只允许公网 https、拒绝回环/内网/保留地址与危险重定向；签名密钥可轮换撤销 |

删除前由服务端提供影响预览（成员/角色/权限/组/当前会话/OAuth 客户端/刷新令牌族/授权
请求/一次性凭证/邀请/Webhook 端点/审计事件计数）；页面与管理 JSON API 还要求显式确认
并经过真实再次认证（敏感操作目录 `application.delete`，绑定目标应用与行版本）。
物理清理不通过在线页面/API 提供：`loginctl app purge` 只允许本地受信操作者，并要求
应用已逻辑删除且超过保留期；失败整体回滚，重复删除/清理按幂等结果处理。

跨应用读写必须在页面与真实服务两层都被拒绝；应用管理员只能操作被授予的那个应用。

## 3. 系统权限键清单（共 51 个）

说明：
- “作用范围”列是直白概括，完整范围/限制由权限目录（含页面展示）提供。
- 权限目录中每项带有“是否已实现”标记，表示**服务端是否已有该权限键对应的真实业务执行
  路径且执行前经服务端授权判定**（不是“页面/领域服务是否存在”的粗略口径）。当前 51 项中
  48 项为已实现；保持未实现的是 3 项：`authorization.check`（联合判定服务在库内已实现，
  步骤 144 的真实 HTTP 黑盒验收未完成，独立服务是否挂载以最终装配为准）、
  `settings.manage`、`diagnostics.read`（没有对应的服务端执行路径）。**这个标记不是功能开关**，接入时以真实服务装配与测试为准，不要据此
  推断某能力完全不可用或已经可用。
- 权限键只增不删、不复用；新增权限必须同步目录、说明与测试。

## 4. 敏感操作策略（与权限键不同）

权限键回答“能不能做”，**敏感操作策略**回答“做之前是否要再次验证、是否要显式确认、
成功后是否要发安全告知”。两者都满足才执行。

- 策略目录在 `internal/policy`，按稳定操作 ID（如 `password.change`、
  `backup.restore`、`audit.purge`）定义默认策略；root 可在页面/受信 Go API 中覆盖，
  但不能取消 `root_only`、审计要求与不可变敏感约束。
- 认证强度分 `none < password < strong`。`strong` 指第二因素/Passkey 等；环境未实现
  该强度时要求它的操作会 **fail-closed**（明确拒绝），不会降级为只输密码。
- 常见默认：修改密码/移除 MFA/注册 Passkey/恢复备份/清理审计等要求近期认证（默认
  300 秒内）；恢复备份、清理审计、修改策略等为 root 专属。

## 5. 页面与当前状态

内置管理页面覆盖：用户管理/注册审核/用户组、角色/权限/委派/有效权限、应用资料/成员/
安全接入/凭证、客服求助/人工恢复审批、敏感操作策略、审计与错误诊断、统计看板、报告、
备份计划与任务。页面都需要宿主注入真实后端；完整后端适配器目前在本模块内部。

**当前限制**：应用/权限/角色等能力已装配为**内置页面**（独立服务默认注册）；应用管理页新增“新建应用”入口（步骤 155，创建后默认停用），应用状态页提供“逻辑删除”（步骤 190：停用前置、影响预览、显式确认与再次认证；删除后数据保留供审计，物理清理仅受控本地/系统通道在保留期后执行）。管理 JSON API（`/admin/v1`）覆盖审计/报告/计划/备份/任务/错误码等，另提供 `POST /applications/{id}/delete`（需 `confirm`、`row_version` 与近期管理强认证）；业务托管管理 API（`/api/managed/v1`，步骤 146–148，默认关闭）提供应用范围受限管理；应用客服 API（`/api/app/v1/support`，步骤 154 代码/开关存在但尚无 dev/审计报告与业务前端验收）默认关闭。外部宿主如需程序化调用需按公开 Go API/契约或上述显式开关接入。页面上的“尚未启用/未提供”是真实状态，不是占位符，不要用假开关掩盖。
