# 客服恢复与账户找回

本文说明用户忘记密码/丢失第二因素时的**受控找回路径**，以及客服、独立审批人与 root
各自能做什么、不能做什么。所有恢复流程都遵守同一条底线：不读取用户秘密、不绕过两步
验证、不单人接管账户。

## 1. 找回路径总览

| 场景 | 路径 | 谁能操作 |
|---|---|---|
| 忘记密码，邮箱可用 | 自助密码找回（向已验证邮箱发一次性链接） | 用户本人 |
| 两步验证设备丢失，有恢复代码 | 用恢复代码替代第二步 → 受限恢复会话 → 重新绑定 | 用户本人 |
| 无法自助，需要人工协助（普通账户） | 客服求助单 → 人工核验恢复申请 → 独立审批 → 受控执行 | 客服 + 独立审批人（不可同一人） |
| root 或高权限账户需要应急 | **不走客服流程**；本地 `loginctl root-recover`（停服/维护 + 排他锁） | 本机应急管理员 |

关键限制：
- 客服**不能**凭电话口述资料、来电号码或单人批准直接接管账户。
- 客服不能读取或设置密码、验证码、重置链接、新密码，不能改邮箱后再重置，不能清除
  两步验证，不能“以该用户身份登录”。
- 目标为 root 或受保护高权限账户时返回 `SUPPORT_TARGET_PROTECTED`，必须转本地应急流程。

## 2. 自助密码找回

1. 用户在登录页发起找回；服务端统一回应“已受理”，**不泄露**该邮箱是否注册。
2. 只有用户此前**已验证**的邮箱才会收到一次性链接；链接用途绑定、限时、单次消费。
3. 用户打开链接完成验证与改密；改密会使相关旧会话/凭证按安全语义失效。
4. 邮件投递失败不改变“密码已修改”这一事实（两者分开记录）；重试有上限。
5. 邮件日志与队列**不得**留下可直接使用的明文恢复入口；只记录脱敏元数据。

实现：`internal/passwordreset`、`internal/mailer`、`internal/session`。真实 SMTP 外发需要
宿主明确配置目标；测试只能使用本仓库的本地捕获器（`internal/testmail`），禁止对真实
用户地址群发测试邮件。

## 3. 恢复代码与受限恢复会话

- 恢复代码在第一步（密码）验证通过后**替代第二步**，不是跳过认证。
- 恢复代码**按组生成**：使用其中一个会作废同组其余代码；过期/已用立即失效。
- 消费恢复代码后只进入**受限恢复会话**（`MFA_REBIND_REQUIRED`）：只能完成新因素绑定等
  恢复动作，不能获得完整业务访问；必须完成绑定并重新正常登录后才恢复完整权限。
- 弱邮箱验证不能替换高权限账户原有的强认证要求。
- 恢复代码是一次性秘密：离线保存，不写日志/工单/聊天，过期或已用后重新生成。

## 4. 客服求助单

流程与页面已实现（`internal/support` + 客服页面）：

1. 客服登记求助单：记录必要核验结果与最小脱敏资料；**历史只追加**，不提供编辑/删除。
2. 目标定位与分派：客服只看到分配给自己的工单与获准的普通目标；不显示电话、完整邮箱、
   密码、验证码、重置链接、Token 或证据原文。
3. 状态流转：待处理 → 处理中 → 已发送/已解决等；每次变化记录操作者与时间。
4. 发送（可选）：只向用户**原已验证邮箱**发送找回入口，并明确告知“密码尚未改变”。
   登记求助单本身不发送邮件；缺少邮件渠道时转人工核验，不伪造“已发送”。

页面不提供“以该用户登录”“改收件地址”“跳过核验”等入口；电话核验风险提示常驻。

## 5. 人工核验恢复（默认关闭）

用于普通账户在无法自助、无法通过客服常规流程完成时的受控恢复。**默认关闭**；关闭时
页面只显示真实原因，不渲染假表单。

1. **发起**：客服在真实配置的核验依据下创建申请；证据摘要只提交一次且不可回读。
2. **独立审批**：审批页在批准表单前显示真正将执行的目标、操作、交付方式、后果与时间
   窗口。发起者/目标本人无写控件，服务端也会拒绝（`RECOVERY_SELF_APPROVAL_DENIED`）。
   未经批准执行返回 `RECOVERY_APPROVAL_REQUIRED`；核验不足返回
   `SUPPORT_IDENTITY_UNVERIFIED`。
3. **时间窗口**：批准有有效期；目标、操作或接收地址改变后原批准失效。
4. **受控执行**：由有执行资格的人执行；执行确认页常驻“确认不是授权”。重复执行在重读
   确认后按幂等处理，不会重复生效。
5. **告知**：恢复完成与通知投递结果分开记录；通知失败不回滚已完成的恢复，但会如实显示。
6. **资格撤销**：审批人或执行人资格被撤销后，读取/批准/执行均被拒绝。

实现：`internal/manualrecovery`（申请、独立审批、受控执行、制度摘要）与客服/审批页面。
当前缺口：候选审批人的“待审批列表”投影未提供（页面明确显示“能力未提供”，不枚举 ID）；
拒绝操作不写批准记录；完整生命周期历史查询未提供。

## 6. root 与高权限账户

root 和高权限管理账户**不进入**客服与人工核验恢复流程。应急路径只有本地
`loginctl root-recover`：

```bat
:: 运行目录：目标服务器本机（不是远程接口）；前提：服务已停止或处于维护状态
loginctl root-recover --database <数据库路径> --reason "<原因>" --service-stopped ^
    --reset-password
```

要点：
- 必须显式声明 `--service-stopped` 或 `--maintenance`，并取得排他锁；不会在服务运行中
  偷偷改库。
- 新密码通过**隐藏输入**取得，不接受命令行参数或环境变量，不打印、不写日志。
- 重置 MFA 与撤销主登录 Passkey 分开：`--revoke-login-passkeys` 默认关闭，需二次确认。
- 撤销凭证、更新安全版本与审计一致完成；操作者与原因写入审计。
- 从 root 政策上，应急恢复不等同于“无提示删除所有 Passkey”，也不提供远程匿名通道。

详见 [root-cli.md](root-cli.md)。

| 客服求助单、目标定位、分派、发送 | 已实现（领域服务 + 页面） |

人工恢复、root 保护与恢复完成后的凭证失效规则属于安全不变量：不要为了“方便”增加
跳过核验、单人审批、恢复后保留旧令牌之类的捷径。
