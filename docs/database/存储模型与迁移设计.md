# 存储模型与迁移设计（步骤 06）

本文是步骤 06 的正式存储契约，也是 `database/0001_design_baseline.sql` 设计基线的落地计划。基线中的 48 张表是设计输入，不是全部在此步骤创建；本步骤只建立隔离核心与迁移机制，其余表在对应步骤通过追加迁移落地。

## 1. 迁移机制

### 1.1 文件与不可变性

- 迁移文件位于仓库根目录 `migrations/`，由包 `migrations` 通过 `go:embed` 内嵌；SQLite 使用 `migrations.SQLite`。
- 文件名必须为 `NNNN_description.sql`：四位数字版本号、小写描述、`.sql` 后缀。版本按字符串升序执行，版本必须唯一。
- 已部署执行的迁移文件不得修改、重命名或删除；只能追加更高版本。执行器对原始文件字节计算 SHA-256 并持久化，内容变化（包括注释）会被拒绝。
- 文件头部（首个 SQL 语句之前）可写指令：
  - `-- +migrate non-transactional`：声明迁移可能包含无法事务回滚的 DDL，执行后失败需人工核对。
  - `-- +migrate whole-file`：整个文件作为一条语句执行，用于触发器或复合语句；默认按分号拆分并忽略注释、正确处理引号内分号。
- 未知指令会报错，避免拼写错误被静默忽略。

### 1.2 迁移记录表（基础设施，不属于用户迁移）

具体数据库后端（SQLite 在步骤 07）负责幂等创建以下记录表；表结构属于迁移基础设施，不进入用户迁移历史：

```sql
CREATE TABLE IF NOT EXISTS schema_history (
  version TEXT PRIMARY KEY NOT NULL,
  description TEXT NOT NULL,
  applied_at_ms INTEGER NOT NULL,
  source_sha256 TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS schema_failures (
  version TEXT PRIMARY KEY NOT NULL,
  description TEXT NOT NULL,
  source_sha256 TEXT NOT NULL,
  failed_at_ms INTEGER NOT NULL,
  error_summary TEXT NOT NULL
);
```

- `schema_history` 只保存成功应用记录；`source_sha256` 与迁移文件字节摘要一致。
- `schema_failures` 保存最近一次失败尝试；错误摘要压成单行并限制长度，后端错误不得包含凭据或密钥。
- 记录表的字段变化必须按兼容性处理，不能用 `IF NOT EXISTS` 掩盖已有表结构差异。

### 1.3 执行规则

1. 获取迁移排他锁（`Backend.Lock`），同一数据库同一时刻只允许一个迁移持有者；锁必须响应 `ctx` 取消。
2. 幂等创建记录表，读取已应用与失败记录。
3. 校验已应用记录是当前迁移列表的严格前缀；版本未知、顺序不符、重复或校验和不一致时拒绝运行。
4. 存在失败记录时拒绝继续，返回 `ErrFailurePending`；必须人工核对数据库结构后调用 `ClearFailure`，执行器不自动清理、不自动重试。
5. 按版本顺序执行待应用迁移；每条记录 `applied_at_ms` 与校验和。
6. 执行失败时持久化 `schema_failures`（尽力在 ctx 取消后仍写入），停止后续迁移，返回已应用子集与错误。
7. 全部已应用时返回 `UpToDate=true`，不重复执行。

### 1.4 事务与 DDL 策略

- 支持事务 DDL 的数据库（SQLite 计划）应在同一事务中执行迁移语句并写入 `schema_history`，失败回滚；本步骤用可控内存后端验证机制，真实 SQLite 事务在步骤 07 实现并测试。
- MySQL 等 DDL 隐式提交的数据库必须声明 `non-transactional`；失败后可能留下部分结构，执行器只记录失败状态，不承诺自动回滚，必须人工核对修复后 `ClearFailure`。
- 不支持事务的方言在 `Backend.Apply` 中逐条执行；不得因为失败而写入已应用记录。

## 3. 主键与关联

- 用户、应用、角色、权限、组、凭证、会话等业务实体使用**服务层生成的不透明文本 ID** 作为主键；不使用自增整数，不把用户名、邮箱或应用名作为外部永久关联键。
- 用户以 `users.id` 被引用；`applications.owner_user_id`、`app_memberships.user_id`、`group_members.user_id`、`user_roles.user_id` 均引用 `users(id)`。任何表都不得对 `username` 建外键。
- `username_normalized` 是服务层按确定规则生成的规范化值，数据库只保证其唯一；原始 `username` 可受控更名，ID 不变。
- 应用以 `applications.id` 被引用；每个应用创建时在同一事务写入一个 `scopes(id,kind='application',app_id)`，系统范围固定为 `id='system'` 且 `app_id IS NULL`。数据库不自动生成应用 scope。
- 角色、权限、用户组都带 `scope_id`。`role_permissions`、`group_roles`、`user_roles` 使用 `(id,scope_id)` 复合外键，使角色/权限/组不能与其他 scope 的对象组合；服务层仍须检查应用成员关系、赋权范围与当前有效权限。
- 应用内资料、成员状态与应用角色按应用隔离；`app_memberships` 主键包含 `app_id`，不能用全局字段代替应用成员关系。
- 系统管理员资格（`users.is_root`）与应用内角色分开；root 唯一索引只保证最多一个，不保证存在，也不阻止直接数据库操作删除，受控初始化在步骤 28。
- 乐观并发使用 `row_version`；时间、状态、删除级联规则见下节。`user_roles.assigned_by`、未来审计字段记录真实操作者，不能填写虚假 root。

隔离边界不是只靠数据库：复合外键阻止跨 scope 组合，但“用户是否为应用成员”“角色是否允许分配给该用户”“当前权限是否仍有效”必须由服务层按可信上下文检查，默认拒绝。

## 4. 跨数据库表示约定

| 主题 | 约定 |
|---|---|
| 主键与 ID | 不透明文本，由服务层生成；跨数据库统一 TEXT/VARCHAR，不使用自增序列作为业务主键 |
| 时间 | UTC Unix 毫秒整数，列名后缀 `_at_ms`；可空表示未发生；界面按用户时区显示 |
| 布尔 | 整数 0/1 并加 CHECK，不依赖数据库 BOOLEAN 类型差异 |
| 二进制 | BLOB/BYTEA 等由方言后端封装；凭证摘要、密文、公钥使用二进制列，不转成十六进制文本存储 |
| 大小写唯一性 | 不使用 SQLite NOCASE 等方言排序规则代替业务规范化；由服务层生成 `*_normalized` 列，数据库只对规范值建唯一索引 |
| JSON | SQLite 使用 `json_valid`；其他方言在适配步骤使用等价约束或应用层校验，不能假定 JSON 函数一致 |
| 外键 | 每个连接显式启用外键；SQLite 计划在步骤 07 对每个连接执行 `PRAGMA foreign_keys=ON`；删除动作按对象语义显式声明 |
| 分页 | 列表默认使用稳定排序键（如 `created_at_ms, id`）的键集游标分页，避免大偏移；游标为不透明字符串，由服务层校验长度与格式；限制最大页大小 |
| 方言差异 | 占位符、标识符引用、DDL、锁、UPSERT、JSON 等差异集中在 `internal/storage` 的具体后端与方言实现；业务层不拼接特定数据库语法 |

## 5. 存储与事务契约

- 迁移执行器只依赖 `internal/storage/migrate.Backend`：排他锁、记录表创建、已应用/失败记录读写、单迁移原子应用。SQLite 在步骤 07 实现该契约。
- 迁移失败记录与已应用记录分离；失败记录必须能在失败事务之外写入，避免“事务回滚把失败证据也回滚掉”。
- 后续业务存储使用标准 `database/sql` 与显式 SQL；不建立全表通用 CRUD 接口，也不引入 ORM。仓储接口按实际业务用例定义在消费方或公开契约位置。
- 宿主传入的数据库连接由宿主拥有；组件自己打开的连接自己关闭，沿用步骤 04 的资源所有权边界。
- 迁移执行器不记录秘密；错误摘要只写脱敏后的单行文本。
