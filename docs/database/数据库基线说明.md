# SQLite 初始结构基线

版本 design-0001，生成日期 2026-11-14。数据库文件已创建，所有业务表为空。只有 system 范围记录和 schema_history 结构来源记录；无 root、默认密码、秘密、角色或权限分配。预设角色和 root 按步骤 27～28 创建。

## 使用定位

本文件、SQL 和 login.db 是供步骤 01、06、07 审查使用的设计输入，不是已经通过 Go 产品测试的数据库。先核对需求与所选驱动，再建立正式迁移。不得因为这里预建了后续表而将对应开发步骤标记完成。SQL 不使用 IF NOT EXISTS 掩盖结构冲突，只用于新数据库。

## 字段约定

- ID 使用服务层生成的稳定不透明文本；用户 ID、应用 ID 和权限标识的不可变性由服务层及后续迁移保护，当前没有保护所有字段的数据库触发器。
- 时间统一 UTC 毫秒整数，业务界面按所选时区显示；生命周期字段后缀 _at_ms。
- 布尔为 0/1，部分枚举使用 CHECK；修改记录用 row_version 支持后续乐观并发控制。
- JSON 字段用于扩展资料和策略，含 json_valid 约束；不是把整个业务模型塞入 JSON。
- username_normalized 由服务层按确定的 Unicode/大小写规则生成，数据库只保证规范值唯一；SQLite NOCASE 不足以替代完整规范化。
- email 登录可选，本基线规定“已验证邮箱全局唯一”，未验证邮箱不参与该唯一索引；这是为避免邮箱登录身份歧义采用的设计默认。电话目前不验证、不参与找回。
- scope_id 为明确的 system 或应用范围；角色和权限使用复合外键保证组合不能跨范围。应用管理员能否赋权、用户是否为应用成员仍需服务层检查。
- 每个应用对应一个 scope，由应用创建事务同时写入；系统范围只有 system。库本身不自动生成应用范围。
- root 唯一索引保证最多一个，不保证至少一个，也不负责阻止直接数据库操作把其删除。受控初始化和 root 保护由后续服务/CLI 实现。
- recovery_approvals 禁止发起人等于批准人，但核验真实性、审批权限、有效期和目标保护必须由服务层执行。
- 密码仅保存密码哈希；高熵 Token 保存摘要；低熵验证码需要受密钥保护的验证方案。_encrypted 字段必须存放含版本的认证密文，key_id 标明外部密钥版本；SQLite 文件本身未启用整库加密。
- notifications 的正文变量可能含一次性链接，因此按密文存储，不作为明文日志。密钥不能存入 settings 或普通 JSON 字段。
- audit_events 不对目标用户、应用、任务建立级联外键，删除对象不应删掉历史；使用快照标识追溯。真正的不可篡改仍需外部保护。
- 作业发起者、执行者和取消者分别记录；定时触发使用唯一索引避免同一时刻重复入队。状态转移和原子取消须后续实现。
- session.security_version 与用户版本仅是撤销机制的一部分；旧备份恢复时两者一起回滚会使凭证复活，正式恢复必须使用库外恢复代际/密钥策略，不能仅比较这两个字段。
- 普通访问日志为文件输出，不要求全部写入审计表；报告二进制、头像和备份放受控存储，数据库保存引用和摘要。

## 尚待详细设计的事项

正式应用迁移编号与本设计版本的认领；各类 JSON 的固定契约；正式索引/查询优化；记录删除和保留策略；签名私钥提供者；消息正文加密方式；备份恢复代际。不得假装建表完成了这些机制。

MySQL、PostgreSQL 和 SQL Server 迁移在计划相应步骤实现，本包不附带未经适配的 SQLite SQL 冒充其他数据库结构。当前库采用默认 DELETE 日志模式作为易携带交付文件；Go 运行时是否启用 WAL，由驱动与事务实现决定，且每个连接必须启用外键。

## 重建与校验

使用 tools/create_database.py 可在一个新的目标路径重建库并登记 SQL 的 SHA-256。直接执行 SQL 只会创建结构及 system 范围；schema_history 记录由建库工具登记，避免 SQL 对自身摘要形成循环。不要编辑已投入正式迁移的 SQL 来伪装结构一致。

SHA256SUMS.txt 是交付包内所有文件的校验清单，不是密码学签名；适合检查意外损坏，不证明发布者身份。
